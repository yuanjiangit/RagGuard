# 复盘草稿：《我给 Java 生态补了一块"验证 RAG"的拼图 —— RagGuard 四个月复盘》

> 状态：素材草稿（发布前需补充真实数据：star 数、用户反馈、稳定性实测数字）。目标渠道：掘金 / 公众号 / 知乎，后译英文版投 Hacker News / r/java。

## 一、起点：一个结构性空白

2026 年年中想给自己的 RAG 应用做回归测试，发现 Python 世界有 Ragas / DeepEval / TruLens 一整层评估生态，而 Java 世界——Spring AI、langchain4j 都很成熟——只有"搭 RAG"的框架，没有"验证 RAG"的框架。换 embedding 模型、改切分策略、调 Prompt 之后效果是变好还是变坏，全靠人工"感觉"，坏改动往往数周后才被用户投诉发现。

这就是 RagGuard 的选题：**把 RAG 评估写成单元测试——效果回退，代码就合并不进去。**

## 二、四个里程碑，各自交了什么

| 里程碑 | 产出 | 最难的决策 |
|---|---|---|
| M0（2 周） | 多模块骨架、CI、两篇公开设计笔记 | 把"通读论文写笔记"当作正式交付物——笔记后来成为 README 之外最有效的信任背书 |
| M1（4 周） | 四个指标引擎 + judge 抽象 | **离线可测性**：judge/嵌入全是接口，指标聚合公式用固定 mock 数据验证，不碰网络——这一条让后续所有改动能放心重构 |
| M2（4 周） | Spring Boot starter、HTML 报告、端到端示例 | **语义分离**：`JUDGE_FAILED`（基础设施故障）与低分（真实质量回退）严格分开，CI 语义才干净 |
| M3（4 周） | 测试集自动生成、langchain4j 适配、GitHub Action | 生成物定位为"**候选清单**"而非一键全自动——测试集是裁判，LLM 生成的题必须过人审 |
| M4（2 周） | 判定缓存、趋势图、中文文档、成本文档 | 成本问题正面回答：缓存 + 便宜模型 + 指标子集，三个杠杆把日常评估成本压到接近零 |

## 三、如果重来，会不一样的三个决定

1. **更早做架构净化**。M3 才把 judge prompt 与解析下沉到 core（双生态复用），M1 时就该想到"框架适配层注定不止一个"。教训：凡是"XX 适配"字样的代码，第一版就要假设它会被抄第二遍。
2. **测试数据比测试逻辑难写十倍**。指标公式一天写完，边界用例（judge 输出不完整、空答案、归因下标缺失）的设计花了三倍时间。评估框架的可信度恰恰全在这些边界里。
3. **设计笔记先于代码公开**。两篇 M0 笔记把"算法口径"提前钉死，避免了实现期反复。以后所有项目照此办理。

## 五、接下来（P2 候选，按用户反馈排序）

切分质量评估（ingestion 层）、历史趋势服务（SQLite + Dashboard）、A/B 回放矩阵、Maven/Gradle 插件。原则不变：**只做"验证 RAG"这一层**，与 Spring AI / langchain4j 互补而非竞争。

## 六、写给同样想做开源库的你

- 选题一句话讲不清的，慎重（"给 RAG 做单元测试"可以）
- 每 2 周必须有一个"能给人看"的产出，否则业余项目必然烂尾
- 中文内容是主场优势，但代码、注释、API 要英文——两者不冲突
- 公开数字（方差、成本、缓存命中）比广告词更有说服力
